# Review of `docs/test_cases.md`

Ниже — ревью тесткейсов как от опытного QA.

## Общая оценка
Текущий набор тестов покрывает базовые сценарии API:
- успешные вычисления;
- часть негативных проверок;
- healthcheck `GET /`.

Но в текущем виде документ **не готов как качественный тестовый артефакт**: есть неоднозначности в контракте, слабая структура, недостаточное негативное покрытие и проблемы с единообразием оформления.

---

## Что хорошо

1. **Есть позитивные и негативные сценарии**
   - валидный запрос;
   - деление на ноль;
   - невалидная операция;
   - отсутствие обязательного поля;
   - некорректный запрос;
   - `GET /`.

2. **Проверены базовые математические операции**
   - сложение;
   - вычитание;
   - умножение;
   - деление.

3. **Есть несколько граничных случаев**
   - отрицательные числа;
   - `0 / 5`;
   - `5 / 0`.

---

## Основные замечания

### 1. Нет единого формата тесткейсов
Сейчас документ больше похож на список заметок, чем на полноценные тесткейсы.

Не хватает стандартной структуры:
- ID теста;
- название;
- предусловия;
- шаги;
- тестовые данные;
- ожидаемый результат;
- приоритет / тип / статус.

Из-за этого кейсы сложно поддерживать и использовать в регрессе.

---

### 2. Неоднозначные типы данных в контракте
В начале указано:

```json
{
  "firstNumber": "number",
  "secondNumber": "number",
  "operation": "string"
}
```

Но во всех примерах числа передаются как строки:

```json
{
  "firstNumber": "1",
  "secondNumber": "1",
  "operation": "+"
}
```

Это критичная неоднозначность.

Нужно явно зафиксировать одно из двух:
- API принимает **числа**;
- API принимает **строки**.

Если по контракту это `number`, то в JSON должно быть:

```json
{
  "firstNumber": 1,
  "secondNumber": 1,
  "operation": "+"
}
```

То же относится к `result` в ответе.

---

### 3. Негативные ответы описаны слишком жёстко и местами неаккуратно
В тестах ожидаются конкретные тексты ошибок:
- `Second number cannot be zero`
- `Invalid operation %`
- `Invalid parametr`
- `Invalid Request`

Проблемы:
- неясно, это официальный контракт API или предположение автора;
- проверка точного текста делает тесты хрупкими;
- есть опечатка: `parametr`.

Рекомендация:
- либо явно зафиксировать контракт ошибок отдельно;
- либо проверять только HTTP-код и структуру ошибки, если текст не критичен.

---

### 4. Не хватает покрытия по валидации входных данных
Сейчас не проверяются многие важные негативные случаи:

#### Для `POST /calculations`
- отсутствие `firstNumber`;
- отсутствие `secondNumber`;
- отсутствие `operation`;
- `null` в полях;
- пустая строка `""`;
- строка из пробелов `"   "`;
- нечисловые значения:
  - `"abc"`;
  - `true`;
  - `[]`;
  - `{}`;
- очень большие числа;
- дробные числа;
- лишние поля в запросе;
- некорректный JSON.

#### Для операций
- `5 - 10 = -5`;
- `-5 + 10 = 5`;
- `-5 * -5 = 25`;
- `0 - 0 = 0`;
- `0 * любое число = 0`;
- деление отрицательных чисел;
- поведение с дробями, если они поддерживаются.

---

### 5. Дублирование сценариев
Некоторые кейсы частично дублируют друг друга:
- кейс 1 и кейс 2 оба проверяют `POST /calculations`;
- кейс 3 частично перекрывает базовую арифметику;
- кейсы 4 и 5 оба проверяют деление.

Это не ошибка, но можно сократить повторения и сделать набор компактнее.

---

### 6. Не хватает проверки HTTP-аспектов
Пока проверяется в основном только `status code` и `body`.

Желательно добавить проверки:
- `Content-Type: application/json`;
- корректный метод (`POST` vs `GET`);
- поведение при неверном endpoint;
- поведение при некорректном формате тела запроса.

---

### 7. Непоследовательное оформление
Есть проблемы с единообразием:
- `Post/calculations` лучше писать как `POST /calculations`;
- `Get/` лучше как `GET /`;
- `Код 200 ОК` лучше как `HTTP 200 OK`;
- `Error: Bad Request` лучше как `HTTP 400 Bad Request`.

Также стоит привести к единому стилю:
- `Предусловие` / `Предусловия`;
- формат JSON;
- оформление списков.

---

## Замечания по отдельным кейсам

### Кейс 1. Отправка запроса с валидными данными
Хороший базовый позитивный кейс.

Что можно улучшить:
- уточнить типы данных в запросе;
- указать точный endpoint в формате `POST /calculations`;
- при необходимости добавить проверку `Content-Type`.

---

### Кейс 2. Проверка перестановки операндов
Полезный кейс для проверки коммутативности `+` и `*`.

Но:
- лучше разделить на 2 отдельных теста;
- сейчас один кейс смешивает две проверки.

Рекомендация:
- отдельный кейс для `+`;
- отдельный кейс для `*`.

---

### Кейс 3. Проверка операций с отрицательными числами
Сценарий полезный, но покрытие слабое.

Не хватает:
- `-1 + 1 = 0`;
- `-1 - 1 = -2`;
- `-1 * -1 = 1`.

Также лучше явно разделить операции на отдельные кейсы.

---

### Кейс 4. Проверка деления нуля на число
Хороший позитивный кейс.

Рекомендация:
- проверить, что тип результата соответствует контракту;
- добавить проверку деления отрицательного нуля / дробей, если это поддерживается.

---

### Кейс 5. Проверка деления на ноль
Хороший негативный кейс.

Что нужно уточнить:
- точный формат ошибки;
- всегда ли должен возвращаться именно этот текст;
- есть ли единый контракт ошибок для всех 400 ответов.

---

### Кейс 6. Отправить запрос с невалидной операцией
Кейс полезный.

Но лучше проверить не только `%`, а несколько вариантов:
- `%`;
- `^`;
- `x`;
- пустую строку;
- `null`.

---

### Кейс 7. Проверка обязательных полей
Кейс хороший, но недостаточный.

Не хватает проверок отсутствия:
- `secondNumber`;
- `operation`.

Также лучше проверить `null` и пустые значения.

---

### Кейс 8. Отправка невалидного запроса
Сценарий полезный, но сейчас он слишком общий.

Нужно уточнить:
- что именно считается невалидным запросом;
- почему пробелы в полях должны давать именно `Invalid Request`;
- что происходит при `""` и `null`.

---

### Кейс 9. Проверка Get запроса
Полезный smoke/healthcheck кейс.

Но лучше оформить как:
- `GET /`;
- ожидаемый `HTTP 200 OK`;
- ответ `{"status":"ok"}`.

Также стоит проверить негативный сценарий для неверного метода, если это важно.

---

## Что я бы рекомендовал исправить в первую очередь

### Обязательно
1. Привести документ к единому шаблону тесткейсов.
2. Уточнить типы данных: числа или строки.
3. Зафиксировать контракт ошибок.
4. Исправить опечатки и унифицировать оформление.
5. Добавить недостающие негативные тесты.

### Желательно
1. Разделить смешанные кейсы на отдельные тесты.
2. Добавить приоритеты и ID.
3. Проверить boundary cases.
4. Расширить покрытие по невалидным типам и пустым значениям.

---

## Итог
Текущий набор тестов показывает, что автор понимает базовую логику API, но как QA-артефакт документ пока сырой.

### Оценка:
- покрытие базовой логики: **6/10**
- оформление: **3/10**
- однозначность: **4/10**
- готовность к использованию в команде: **низкая**

Если хочешь, я могу следующим сообщением:
- **переписать эти тесткейсы в нормальный QA-формат**, или
- **сделать более строгий review с правками по каждому кейсу**.
